# Architecture

How the game is put together, where each kind of code lives, and the rules
that keep it deterministic. Topic docs (listed at the end) go deeper.

The game is a React + Phaser browser app over one deterministic engine. The
same engine runs in the browser, in Node tests, in replay and under the agent
(MCP) runner. Model-written prose is optional and always has a local fallback.

## Where code lives

| Path | Owns |
|---|---|
| `src/core/` | Game state, rules and commands. `engine.ts` is the authority on what happens. Also time (`core/time/`), plots, kin, health, fauna, routing, topography. |
| `src/world/` | World generation. `v3/` builds the local scene (`v3/generate.ts`, `v3/plan.ts` for settlements). `geography/` is shared Earth geography. `regional/` holds regional constraints for the planner. `travel/` holds the map squares and journeys. `worker.ts` runs generation off the main thread. Interiors, caves, sewers and ships sit at the top level. |
| `src/content/` | Data and the resolvers that pick from it: history, geography, characters, beliefs, plots, cards, economy, props, settlements, ecology, fauna. |
| `src/runtime/` | The live session (`session.ts`, `Runtime`), save and manifest schema (`schema.ts`), world preparation (`preparation.ts`, `prepared-store.ts`), map travel (`map-travel.ts`) and the autopilot. |
| `src/render/` | The Phaser view (`WorldScene.ts`) and its painters, rasters and workers. |
| `src/ui/` | React screens: `App.tsx`, panels, cards, modals. |
| `src/audio/` | Music, ambience and effects. |
| `src/narrator/`, `server/`, `api/` | Model calls. `api/*.ts` are the Vercel endpoints. They wrap `server/*.ts`. |
| `src/agents/` + `scripts/agent.ts` | The agent tool set, its loop and run records. |
| `src/edu/` | Classroom mode. |
| `src/chronicle/` | The agent-turn chronicle. This is unrelated to the in-game years. |
| `src/dev/` | Labs, served at routes such as `/terrain-lab`, `/prop-lab` and `/character-lab` (see `src/main.tsx`). |
| `scripts/art/` | The Python art pipeline. It writes the atlases in `public/packs/`. |

`src/core` should not import from `src/render`. Today it does in three places:

- `engine.ts` imports `fence-pass`.
- `cave.ts` imports `edge-faces`.
- `sewer.ts` imports `carriageway`.

Do not add more. Moving those helpers into `core` or `world` is welcome. Core also imports a lot of `content` and some `world`. That is accepted.

## One path for every change of state

Everything the player or an agent does is a `PlayerCommand` (`src/core/types.ts`):

- It is wrapped in a `CommandRequest {actionId, expectedRevision, command}`.
- `engine.act` applies it and returns a `CommandResult` with a status of `completed`, `interrupted` or `rejected`.
- Receipts keyed by `actionId` make a repeated request harmless.
- `engine.observe()` and `engine.inspect(id)` read state without changing it.

The UI, the agent tools and replay all use this path. Do not mutate state from React, Phaser or a tool handler.

## Determinism

- Randomness comes from `random(seed, ...keys)` (`src/core/random.ts`) or `engine.rng(key)`. The counter is saved, and `stateHash` checks it.
- There is no `Math.random` or `Date.now` in `src/core`. The autopilot (`src/runtime/autopilot.ts`) still uses `Math.random`, which is a known exception.
- Model output enters the game as commands, mostly `narrate`, which carries `Intent`s such as `converse`. Those commands are logged, so replay never calls the model again.
- The renderer reads snapshots. It owns the camera, animation and wall-clock time, and never decides an outcome.

## Generation and revisions

New worlds use generator 3 (`createSettlementWorld`, `src/world/v3/`). Terrain, vegetation, hydrology and urban form have one model each. `integratedSetting` in `src/content/geography/defaults.ts` still pins a few revision fields (ecology, roads, streets, placement, characters, worksites and so on); the world doc lists them.

Generator 1 (`src/world/generate.ts`, with the `roman` and `neolithic` packs from `src/content/legacy-packs.ts`) stays as a small authored town for mechanics tests and the building lab. No playable world uses it.

The remaining revision branches exist so old records replay. **Nobody's saves depend on them yet.** Do not add a new revision gate when you change generation: change the current behaviour in place, and bump `PREPARED_VERSION` (`src/world/v3/prepared.ts`) when cached worlds would be wrong. When you work in an area that has old branches, deleting them and their tests is part of the job.

## Complexes

Caves, sewers, mines, world's fairs and tombs are complexes: areas generated from the seed one at a time and walked between.

- `world/complex.ts` holds the shape every area shares: exits (edge strips and doorways that take the player to the matching exit of another area, `exitAt`, `arrivalFrom`) and lifts (a stair, rope or shaft used with the action key).
- `core/complex.ts` holds the one run (`state.complex`), the record of each complex (`state.complexes`: finds taken, kills, areas walked), the host, and `KINDS`: one row per kind, which the engine's calls are routed through. A new kind is a row there, a generator in `world/`, a module in `core/` and a view.
- The same file holds what the walked kinds (fairs, tombs) share: `cachedArea`, `arriveIn` (land beside the exit or lift that leads back, note the area as walked), `areaTarget` (lifts and things in reach), `burnLight`, and `complexMap`, which lays the walked areas out by the side each way leaves from and shows the unwalked ones their ways lead to as "?". The sidebar draws it in place of the street map (`AreaMap` in `ui/Minimap.tsx`).
- Caves and sewers are still stacks of levels with their own level caches and arrival; they use the kind table, `takeFind` and `burnLight` but not exits.
- `render/lamplight.ts` lights the underground kinds' views and draws their lamp gauge. `WorldScene` has one slot, `areaView`, for the view of a fair's or a tomb's area.

A palace is planned and walked exactly as a fair is, and is a `Fair` in data: `content/palaces/versailles.ts` is Versailles from 1701, fifteen rooms and courts by rectangle from the forecourt to the Latona fountain, entered by a prompt naming it. Buckingham Palace and the White House are planned the same way. What makes it a palace is content: the `palace` look, painted in `render/fair/palace.ts`: a back wall seven cells tall set out in bays three cells wide (`palaceBays` in `world/fair.ts`), each bay an arch of mirror, a damask hanging with a picture, or a doorway with gilt leaves, between piers faced with red marble under a gilt entablature; parquet de Versailles in panels a bay square, or black and white marble; window light on the floor. A palace room is furnished against its walls, not in rows: pier tables with candlesticks and porcelain, stools, busts, benches, candle stands, orange trees in tubs (`paintPalaceDecor`), and the room's own piece once (`FURNITURE` in `render/fair/things.ts`: chimneypiece, altar, stand of arms, bureau). How a palace room is built, coloured and furnished is a `PalaceStyle` (`content/palaces/styles.ts`): ramps for the panelling, the mouldings, the furniture frames, the pier stone and the cloth; inset or fluted piers; a floor of parquet panels, herringbone, marble or carpet; the pattern of bays along the back wall (mirror, hanging, painted panel with a picture, sash window with curtains, bookcase, chimneypiece); and what the room is for, which picks its furniture in `world/fair.ts` from one table per order. The great rooms are gallery, ballroom, drawing room, dining room, library and office; the rooms round them are bedchamber, antechamber, guard room, vestibule, chapel, kitchen, bath and closet, each with its own piece (a state bed or a lord's bed, an altar, arms racks, a dresser and a pot over the fire, a copper bath or a stave tub, a Roman cooking bench). A palace room may be as small as 14 cells by 13. A room that says which rooms it `opens` to has no door to any other that adjoins it, which is how a bedchamber is reached only through its antechamber. A palace sets one style (`palace` on the `Fair`) and a room overrides what differs (`palace` on the area), so one painter does Versailles (`louisQuatorze`), Buckingham Palace from 1856 (`victorianState`, `content/palaces/buckingham.ts`) and the President's House from 1818 (`federal`, `content/palaces/white-house.ts`). `content/palaces/kit.ts` holds the makers the three plans share. A new palace is a style, a list of rectangles and its people. A style's `order` says how the room is built. `classical` is the piers and cornice above. `timber` is a hall (`neolithicHall`, `meadHall`): the underside of the thatch on its rafters, daub or planks between braced posts, bays hung with weavings, shields, hides, antlers or shelves of pots, a beaten earth floor lit from its fires, and for furniture a high seat on the long wall, wall benches, looms, racks, pots and querns, two rows of roof posts, trestle boards and long hearths that burn in frames; a hall is dimmer than a palace room and its fires and torches glow. `roman` is a house of the late Republic and Empire (`romanHouse`): plastered walls painted in panels of the room's two colours between dark bands with gilded candelabra, over a dark dado and under a pale zone of garlands; bays may also be a painted garden, the household shrine or a cupboard of book rolls; doorways hung with a curtain; floors of black and white mosaic or red signinum. `pillared` is a hall of free-standing columns (`egyptianPalace`, `persianPalace`, `aegeanPalace`), and `columns` on the style says whose: bundled papyrus under an open bell, a fluted shaft carrying two bulls, or a red shaft narrowing downward under a cushion. The same choice sets the cornice (striped cavetto, battlements over glazed rosettes, beam ends over a running wave), the dado, and how the bays are painted (`relief`, people in file carrying gifts; `beast`, a lion on a coloured ground; `bands` of pattern), all in `pillaredBack`. Floors are painted plaster or stone flags. The columns stand in rows down the hall with the way to the throne clear between them; a throne on a dais is the hall's own piece; an Aegean hall has its round hearth with four columns round it instead of rows. `screened` is a timber frame filled with screens (`chinesePalace`, `shoinPalace`), painted by `screenedBack`; `columns` again says whose. `lacquer` is a Chinese hall of the Ming and Qing: red posts on stone drums, bracket sets and a beam painted blue and green with gold, bays of lattice window, ink landscape or hanging scroll, grey brick underfoot, posts in rows down the hall and a gilded throne before a screen of five leaves. `cypress` is a Japanese hall about 1600: squared bare posts under a transom, bays of paper screen, gold-leaf screen with a pine, or an alcove with a scroll and one branch, straw mats (`tatami`), no posts on the floor, cushions in two files before a raised seat with a gold folding screen behind it. Its furniture is lanterns, cushions, low tables, folding screens, chests, and bedding laid on the mats. Roman rooms are built round an opening in the roof (`court` on the level): the atrium's pool in its marble rim (a bath has a smaller one to plunge in), and the peristyle's garden with columns along it; daylight on the floor is brightest there. Its furniture is couches (three round a table in a dining room), a marble table at the head of the pool, the strongbox, lamp stands, folding stools, basins and a writing table. Palace furniture is props, not scenery: `content/props/palace.ts` defines each piece in the prop catalogue (what is carried, what topples, what breaks, the strongbox as a container, `seat` and `burns`), `world/fair.ts` lists them on the level (`props`), and `arriveIn` puts them in `state.objects` the first time an area is walked into, so carrying, striking, shoving, toppling, opening and sitting are the map's own code. They are drawn by the main scene from their sprite name (`made:palace:<fair>:<area>:<kind>:<n>`, painted on demand by `palacePropPicture`); `@<px>` on the name stands a thing on a table until it is picked up. Fixed pieces keep their cells closed in the plan; movable ones block as props, and the people in the room walk round them. Columns, posts, hearths and the laid dining table are still scenery. Exhibits are props as well (`content/props/exhibits.ts`), each with the act its find gives it; `AreaThing.prop` marks the plan entry whose object in the world is what is drawn and used. Palaces nobody drew are planned in `content/palaces/plan.ts`: a kind is a recipe that, from a seed, chooses its rooms and sets them out in rows from the gate inward (`setOut`, in cells; a room may be shallower than its row, rooms may be stacked in one width, and a gap leaves a width empty); each kind is expanded into four plans at load, flagged `generated`. Each kind is laid out as its builders laid it out. A manor (`manorPlan`) is the hall between its two ends: the lord's chamber and sometimes a chapel past the high table, the buttery, pantry and a kitchen apart past the door. A Baroque palace (`enfiladePlan`) has the working rooms across the court front and, on the garden front, two apartments either side of a great room, each a row that grows smaller and more private: guard room, antechamber, bedchamber, cabinet. A nineteenth-century great house (`corridorPlan`) has every room off one corridor and a bathroom with the bedroom. A kind may be `within` a part of the world, outside which a prompt does not find it. A prompt that asks for a kind (`asks`, e.g. warlord, chieftain, mead hall) starts in one of the plans whose years hold the date, picked by the world seed (`venueFor`, carried as `venue` on the setting); asked for at a date no kind covers, the start is an ordinary one. A kind also lists the posts of its household (`posts` on the `Fair`: a title, the words that ask for it, the livelihood it is worked as, its share of the household): the ruler, guards, scribes, servants, cooks and whoever else that court had, under their own names (palace eunuch, keeper of the knots, usher of the hall, fan-bearer). A prompt about a ruler or anyone of a court ("a late medieval king", "an Aztec noble", "a palace guard in Beijing, 1750", "a footman in Paris, 1700") starts in the palace that stood there then, in that post, with its work as the start brief (`postFor`); the ruler or courtier must be who the prompt is about, so "a baker serving the king" and "King Street" start as before. And a quarter of those who start in a city and name no work begin in its ruler's household, in a post drawn by its share (`courtStart`, `COURT_SHARE`). The World Weaver endpoint works the palace out again for the place, year and person it chose (`server/world-weaver.ts`), so a ruler or courtier it invents also starts at court. There are three hall kinds: the Neolithic big house, the chieftain's hall to AD 499, the lord's hall to 1150 (the last two with the lord's own chamber beside the hall). After them come the manor (`manor`, 1151 to 1520: manor, baron, great hall), the Baroque palace (`palace-baroque`, 1650 to 1789: palace, château, schloss, palazzo) and the great house (`palace-house`, 1790 to 1914: the same words, country house, stately home), all in Europe only. Three kinds share the processional plan (`axisPlan`): a court, a porch with the guard and a store off it, the hall of columns with the throne at its far end and a store and the kitchen off its sides, and behind the throne the ruler's chamber, its bath and a shrine. They are the Egyptian palace (`palace-egypt`, 1550 to 332 BC: pharaoh, vizier, or a palace in Egypt), the Persian (`palace-persia`, 550 to 330 BC: great king, satrap, Persepolis) and the Mycenaean (`palace-aegean`, 1450 to 1150 BC: wanax, megaron, Knossos, Mycenae, Pylos), each only in its own part of the world. Two more kinds are screened halls. The Chinese palace (`palace-china`, 1368 to 1911: emperor, mandarin, eunuch, Forbidden City) is courts one behind another on a line from the south gate (`courtAxisPlan`): an outer court with a waiting hall and a storehouse down its sides and the audience hall across its head, then an inner court with the kitchen and a side hall, and the bedchamber, bath and ancestral hall behind. The Japanese palace (`palace-japan`, 1580 to 1868: shogun, daimyo) sets its rooms corner to corner, each further back and further in (`shoinPlan`): the retainers' room, the great room, the inner room and the lord's own room, the last three giving onto a garden. Four more kinds are variants of those sets, each a style and a plan. A king's castle (`palace-gothic`, 1151 to 1649, Europe: `gothicHall`, `castlePlan`) is the timber hall with `walling: "stone"`: coursed stone under oak boards, bays of pointed coloured-glass windows (`lancet`), stone flags; the ward, the great hall, then the great chamber and the privy chamber beyond the high table, the chapel behind, the service past the other end. An Inca's house (`palace-inca`, 1400 to 1533: `incaHall`) is the same hall with `walling: "ashlar"`: fitted blocks with niches under thatch, no wall posts, nothing of iron. An Islamic palace (`palace-islamic`, 700 to 1900, from Spain to India: `islamicPalace`, `divanPlan`) is the pillared hall with `moorish` columns: carved plaster over a dado of cut tile, a band of writing, bays of horseshoe arch and wooden lattice, carpets and cushions and no columns indoors; its courts lie one behind another, the council off a court with a pool, the ruler's hall, then the household's garden court. A Mexica palace (`palace-mexica`, 1325 to 1521: `mexicaPalace`) is the pillared hall with `mexica` piers of banded stucco under a frieze of discs and frets. The Inca and Mexica houses use the processional plan (`axisPlan`), which takes its wall bays and working floors from the court's data. Kinds named by their people come before the ones any "palace" would mean, so an undated prompt finds the right one. The Roman house (`domus`, 60 BC to AD 480, and `domus-early` before it) is asked for by caesar, senator, patrician, consul, domus or "Roman house": an entrance passage from the street, the atrium with bedrooms that open only to it, dining room and tablinum behind, and the garden court at the back with the kitchen and a private bath off it. A yard (`rustic` on a court) is trodden earth with the map's own wattle fence painted round it (`render/boundary-forms.ts`) and the map's own props and trees stood in it by frame name (decor `atlas:<frame>:<cells>`, shown from the game's sheets by `FairView`). Its sprites take a soft edge in a deeper shade of their own colour, not the dark outline. Also room classes whose tables hold vases, clocks, busts, arms or plate, a throne and a bed of state, and a court of people with real livelihoods. The kind, the space ids and the types still say "fair"; renaming them to something that covers both is owed. Doors are not yet closed by rank.

A tomb is planned from the seed (`tombPlan` in `world/tomb.ts`): areas on one axis from the entrance stair to the burial chamber, a shaft where a well room breaks the axis, side rooms off it, some doorways walled up, and the finds for each area with the prizes in the burial chamber. Each area is a main room by its role (`TombRole`), passages to its neighbours and small rooms off its sides. A tradition of tomb building is a `TombStyle` in `content/tombs/`: where and when, what the rooms are called, and the finds with their evidence labels. The only one so far is the New Kingdom rock-cut tomb at Thebes. `core/tomb.ts` is the lamp, the ropes, breaking through a blocked doorway and taking finds; `render/tomb/` paints rock, painted walls and grave goods. A prompt naming a tomb starts the life on its stair (`below: "tomb"`); nothing in the open world leads into one yet.

A fair is a `Fair` in `content/fairs/`: its areas, its own finds, people, coin, the words a prompt names it by, and what is said at its gate. There are two ways to plan one, and a fair may mix them.

- **From a map.** Each area has `at`, its rectangle on the fair's plan (north up, in plan units), and a kind: `gallery` or `court`. `world/fair.ts` sizes the area from the rectangle (`Fair.scale` cells to a unit, within what a couple of screens hold) and `fairWays` joins it to every area whose rectangle shares at least two units of an edge, with a doorway placed as far along the wall as the shared stretch lies. A gallery is a floor of stands by the tags of its class, or of working machines from the kit (`machinery`). It is painted as an exhibition shed: boards underfoot with sunlight from the roof lantern, a back wall of iron columns, round-headed windows and bunting, and a signboard over each doorway. Most of its floor is display tables (`table:<class>:<w>x<h>`): broad low tables seen from a little above, some laid with cloth, with one exhibit to a cell from `render/fair/items.ts`, a library of about sixty small objects each drawn with its own outline and listed by class (loaves, hams and tins for food; hats, boots and bolts of cloth for dress; globes, slates and inkwells for the school), so every table is laid differently. Three-cell tables run down the side walls. Between the tables, its stands are drawn for their class (`stall:food`, `stall:dress`) with that trade's colours and something of its own beside each: a barrel and sack, a dress form, a stove alight, a globe; a court is walks round railed gardens with a fountain or bandstands. The people are generated characters with real livelihoods (`people.ts`): a find may name who is posted at it (`staff`), a fair names who minds filler stands by class (`Fair.staff`), a court's bandstands hold a band (`band`), and the crowd is drawn from the area's `people` in numbers that grow with its size. Sellers trade through the ordinary `deal`, so a baker's loaf is the game's bread. The 1884 International Health Exhibition (`london-1884.ts`) is transcribed this way from its official General Plan; turning a map image into such a plan is not built.
- **By hand.** Paris 1889: each area names its neighbour through each edge (`links`) and its buildings.

A fixed exhibit with `on: "table"` occupies its own space on a shared display table. Its sprite has a hover label and opens a focus card with source and photo links. Paris’s Galleries of Various Industries show Hollerith’s tabulator and a Remington Standard. London’s Dwelling Fittings gallery shows a freestanding Doulton water filter.

Catalog finds with `on: "case"` are grouped by gallery and subject. `world/fair.ts` stocks glass cases from those groups using the area seed and places the cases along the regular aisles. Hover over a case to see its subject or over an item to see its name. Selecting a case lists its contents, and selecting an item opens the catalog page link and any available photograph or period illustration. The historical catalogs document the objects and makers. The grouping within cases and their positions in the galleries are generated. Paris uses the US commission catalog, London the International Health Exhibition’s official catalog, and Chicago’s official directory supplies a compressed Court of Honor and three galleries.

The small objects share the `render/fair/items.ts` painter with the anonymous tables. A catalog entry selects a silhouette and may pin its material variant. Selected objects have their own silhouettes, including the box Kodak, Waterbury Long Wind, Sheffield tooth-cream tube, portable metal filter, and Heinz pickle charm. Pixel details reconstruct the objects at display scale. A linked museum example can document an appearance while the official catalog documents the maker’s participation.

Catalog cases have broad felt-lined tops, shallow wooden fronts, and up to two rows of individually selectable objects. `paintFairCase` supplies the cabinet and object positions to both the game view and `npm run capture:interiors -- fair`, which exports the contact sheet to `artifacts/interiors/fairs.png`.

Reusable exhibit families vary shapes and materials through the same seeded variant used for color. Handheld objects such as books, bowls, and bottles use the small-object painter and fit inside cases. Baths, washstands, stoves, cupboards, tanks, sanitary fittings, workbenches, sewing machines, chairs, mattresses, hall clocks, and filters use the floor painter with collision footprints from `FAIR_SIZES`. Clothing is displayed on stands and curtains hang on walls. Catalog entries can pin a material variant. Floor exhibits are selected once per area from the seed and retain hover labels and source links. The miniature furnishing sprites have been removed from the case-object library. `npm run capture:interiors -- fair-variants` exports the small objects, standalone furnishings, and an adult reference at one common pixel scale to `artifacts/interiors/fair-variants.png`.

A hand-planned area has an archetype (grounds, bridge, hall, pavilion, machines, platform) that `world/fair.ts` lays out, edge links, the buildings along its top whose doors lead to their interiors, lifts, fixed exhibits and tags that draw filler stands. The building fronts are `scripts/art/front_fair.py`, one painter per `PavilionStyle`, baked to the `fair` sheet (`npm run art:fair`); ground, exhibits and decor are painted in `render/fair/`. Closed lawns become railed gardens (parterre, oval walk, open lawn, ribbon bed), mirrored across the avenue and drawn at the pixel over their cells, so walks curve and beds round off while the cells still decide where one can walk. A pavilion interior is painted as a cutaway, its back wall, flag and front steps drawn round the floor and its grounds round that. Halls fill their bays with exhibitors' stands and trophies under a bannered gallery; the Machines gallery sets its exhibits on islands of darker floor between the feet of its arched ribs. Its engines, dynamos, pumps and belt-driven line shaft come from `render/machines.ts`, a kit of working machinery painted as loops of frames (`paintMachine(kind, w, h, v)`) that is not tied to the fair; the view plays the frames. The Tower's far feet lean in under the great arch and its near feet lean out and fade overhead, so the ground under it stays open. A prompt naming the fair starts the life at its gate (`below: "fair"`).

A new kind of large interior plugs in at those three places. Do not start a parallel system for it.

A tower is not a complex. Its storeys are ordinary interiors, so the people who work there have desks, regulars and a day like any other building's. Storey n of a place is the space `<place>@<n>` (`world/tower.ts`: `floorSpace`, `parseFloor`), and `interiorOf` builds it from the tower's plan: which firm has the floor, its interior profile and colouring. A `TowerStyle` in `content/towers/` is the architecture: the frames that are towers, the storeys of the tallest, the lift, the lobby and the rooms a storey can be fitted out as. A skyscraper frame's model publishes the floors it is drawn with (`stories`); the tall form is the look's full height and the others half to four fifths of it, and the tower has storeys in proportion. A building of four or more drawn storeys that is not a skyscraper gets one storey per drawn floor from `blockStyle` (`content/towers/blocks.ts`): named "Offices", it is an office building let floor by floor over an entrance hall; a modern block with a household in it keeps that household's rooms on the street floor and has flats above. Without a lift (before 1890, or flats under six storeys) the way up is the stairs. Who rents them is `content/towers/tenants.ts`: kinds of firm scoped by years and region (no software houses in 1925, no law firms in a Soviet ministry tower), each naming itself from patterns with local surnames and employing a staff of livelihood ids. Each storey is also a workplace (`workplacesIn` in `world/v3/employment.ts` offers one per floor, for its day staff's livelihoods), so a resident or the player can be employed on the 23rd floor, and the "workplace" step of the day lands at a desk there. A tenant keeps its own hours: brokers start early, newspapers work into the night, and after closing a share of the staff stay late (`overtime`, a scoped share: high in postwar Japan, low in the Soviet Union). Flats and hotel floors (`stay`) hold residents or guests instead of staff. While the player is on a storey, `towerStaff` in the engine makes its staff as generated characters, seeded by storey and desk so the same people come back, with those working late, night staff after hours, and fewer when residents already work there. Beside a lift door the action key opens `ui/TowerSection.tsx`, the tower in section, and choosing a floor rides there (the `lift` action). The style's `section` gives the cutaway its stone, setbacks and crown.
